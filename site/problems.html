Pod will not start

ImagePullBackOff / ErrImagePull

Symptom

The Pod shows ErrImagePull, then ImagePullBackOff, and its container never starts.

Error or output

Failed to pull image "ngnix:1.27": rpc error: code = Unknown desc = failed to pull and unpack image "docker.io/library/ngnix:1.27": failed to resolve reference "docker.io/library/ngnix:1.27": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
Error: ErrImagePull
Back-off pulling image "ngnix:1.27"
Error: ImagePullBackOff

Why it happens

The node cannot download the image.

  • Typo in the image name or tag
  • The tag was never pushed
  • Private registry without imagePullSecrets (401/403 in the event)
  • Registry rate limits (429)

Confirm with

kubectl describe pod <pod>   # the exact pull error
kubectl get pod <pod> -o jsonpath='{.spec.containers[*].image}'

Fix

  1. Correct the image on the Deployment, not the Pod: kubectl set image deployment/<name> <container>=<image>:<tag>.
  2. For a private registry, create a pull Secret (kubectl create secret docker-registry <name> --docker-server=<registry> ...) and list it under imagePullSecrets, or on the ServiceAccount.
  3. For 429 toomanyrequests, see the rate limit entry: pull through a mirror or authenticate.

Prevent it

  • Deploy only tags your pipeline has just pushed, and fail the pipeline if the push fails.
  • Attach pull Secrets to the namespace's ServiceAccount, so every Pod there gets them.

CreateContainerConfigError

Symptom

The Pod shows CreateContainerConfigError and never starts; there are no logs.

Error or output

Warning  Failed  kubelet  Error: configmap "menu-config" not found
Warning  Failed  kubelet  Error: couldn't find key DB_PASSWORD in Secret kitchen/db
Warning  Failed  kubelet  Error: container has runAsNonRoot and image will run as root

Why it happens

The container cannot be created because something it references is missing or invalid.

  • Missing ConfigMap or Secret
  • A key name that differs (keys are case sensitive)
  • runAsNonRoot set on an image that runs as root, without runAsUser

Confirm with

kubectl describe pod <pod>   # the Failed event names it
kubectl get configmap,secret
kubectl get configmap <name> -o yaml

Fix

  1. Create the missing ConfigMap or Secret in the Pod's namespace, or correct the name the Pod references.
  2. Match the key exactly: keys are case sensitive (kubectl get secret <name> -o jsonpath='{.data}').
  3. For runAsNonRoot, set a numeric runAsUser, or use an image that runs as a non-root user.

Prevent it

  • Ship the ConfigMaps and Secrets in the same release as the Deployment that reads them.
  • Mark optional references optional: true, and only those.

StartError, exit code 128, empty logs

Symptom

The container never starts; kubectl logs is empty and Last State shows StartError with exit code 128.

Error or output

Error: failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: exec: "ngnix": executable file not found in $PATH: unknown

Why it happens

The container's process could not even be started, so there is nothing to log.

  • A typo in command or args (executable file not found in $PATH)
  • A script without execute permission, or with Windows line endings
  • The binary is missing from the image (a slim or distroless base)

Confirm with

kubectl describe pod <pod>   # Last State, Reason, Exit Code and the Failed event
kubectl get deploy <name> -o jsonpath='{.spec.template.spec.containers[0].command}'

Fix

  1. Correct the command or args on the Deployment, using a binary that exists in the image.
  2. For a script, make it executable in the image, and save it with Unix line endings.
  3. Check what the image contains: docker run --rm --entrypoint ls <image> /usr/local/bin.

Prevent it

  • Start the image with its real command in CI before deploying it.
  • Prefer the image's own ENTRYPOINT over overriding command in the manifest.

exec format error

Symptom

The container exits at once and its only log line is exec format error.

Error or output

exec /usr/local/bin/invoice: exec format error

Why it happens

The image was built for another CPU architecture than the node's.

  • An image built on an Apple Silicon (arm64) laptop running on amd64 nodes, or the reverse
  • A single-architecture tag pushed over a multi-arch one
  • A mixed cluster without a nodeSelector on kubernetes.io/arch

Confirm with

kubectl get nodes -L kubernetes.io/arch
docker buildx imagetools inspect <image>   # its platforms
docker buildx build --platform linux/amd64,linux/arm64 -t <image> --push .

Fix

  1. Build for the nodes' architecture, or for both: docker buildx build --platform linux/amd64,linux/arm64 -t <image> --push ..
  2. Check the tag's platforms: docker buildx imagetools inspect <image>.
  3. In a mixed cluster, select the right nodes with nodeSelector kubernetes.io/arch.

Prevent it

  • Build images in CI, for every architecture you run, never from a laptop.
  • Never push a single-architecture build over a multi-arch tag.

Now learn it: break and fix it yourself in Wrong CPU architecture, then take Level 01 · Pods that will not start on a real cluster. Open this in the interactive reference.

Init:0/1 (or Init:CrashLoopBackOff)

Symptom

The Pod stays at Init:0/1 (or Init:CrashLoopBackOff), and the app container never starts.

Error or output

menu-5b8d9c6f7-tw4kp   0/1   Init:0/1                0             5m
menu-5b8d9c6f7-tw4kp   0/1   Init:CrashLoopBackOff   4 (30s ago)   5m

Why it happens

An init container has not finished, so the app containers have not started.

  • It waits for a Service or DNS name that does not exist
  • It waits for a dependency that is down
  • Its own command fails (Init:CrashLoopBackOff)

Confirm with

kubectl describe pod <pod>   # Init Containers
kubectl logs <pod> -c <init-container>
kubectl get svc

Fix

  1. Read the init container's logs: kubectl logs <pod> -c <init-container>.
  2. If it waits for a Service, create that Service or correct the name it waits for (<svc>.<namespace> across namespaces).
  3. If its own command fails, fix the command; init containers must exit 0 for the Pod to go on.

Prevent it

  • Give wait loops a timeout and a log line that names what they wait for.
  • Prefer retries in the app over init containers that block on other services.

ContainerCreating (for minutes)

Symptom

The Pod stays in ContainerCreating for minutes; logs are empty because nothing has started.

Error or output

Warning  FailedMount  kubelet  MountVolume.SetUp failed for volume "tls" : secret "menu-tls" not found
Warning  FailedMount  kubelet  Unable to attach or mount volumes: unmounted volumes=[tls], unattached volumes=[tls kube-api-access-8x2lp]: timed out waiting for the condition

Why it happens

Stuck before the container can start, usually on volumes or networking.

  • A mounted ConfigMap or Secret does not exist (FailedMount)
  • A volume still attached to another node (Multi-Attach error)
  • CNI problems assigning an IP

Confirm with

kubectl describe pod <pod>   # FailedMount / FailedAttachVolume
kubectl get secrets,configmaps   # in this namespace
kubectl get events --sort-by=.lastTimestamp

Fix

  1. Create the Secret or ConfigMap the volume mounts, in the Pod's namespace, or correct its name.
  2. For FailedAttachVolume or Multi-Attach, see the Multi-Attach entry: the volume is still held by another node.
  3. For sandbox or network errors, check the CNI Pods in kube-system on that node.

Prevent it

  • Deploy the objects a Pod mounts before, or together with, the Pod.
  • Alert on Pods in ContainerCreating for more than a few minutes.

Multi-Attach error for volume

Symptom

A new Pod stays in ContainerCreating during a rollout, waiting for a volume the old Pod still holds.

Error or output

Warning  FailedAttachVolume  attachdetach-controller  Multi-Attach error for volume "pvc-<uid>" Volume is already used by pod(s) orders-6c9b7f5d4-qx8zm

Why it happens

A ReadWriteOnce volume is still attached to another node, so the new Pod cannot mount it.

  • A RollingUpdate starts the new Pod before the old one, which keeps the volume
  • The old node died and the volume has not been detached yet (it takes about six minutes)
  • More than one replica sharing one ReadWriteOnce claim

Confirm with

kubectl get pods -o wide   # old and new Pod on different nodes
kubectl describe pod <new-pod>   # FailedAttachVolume
kubectl patch deployment <name> -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'

Fix

  1. For a single-replica app on a ReadWriteOnce volume, use the Recreate strategy: the old Pod stops before the new one starts.
  2. If the old node died, wait for the detach (about six minutes), or delete the dead node object.
  3. For many replicas, use a StatefulSet with one claim per replica, or ReadWriteMany storage.

Prevent it

  • Use StatefulSets for apps that own a disk.
  • Never share one ReadWriteOnce claim between replicas.

ImagePullBackOff: 429 toomanyrequests

Symptom

Many Pods fail to pull public images at once, often during a scale-out or node upgrade.

Error or output

Failed to pull image "nginx:1.27": ... 429 Too Many Requests - Server message: toomanyrequests: You have reached your unauthenticated pull rate limit. https://www.docker.com/increase-rate-limit

Why it happens

Docker Hub refused the pull: the anonymous rate limit for the cluster's public IP is used up.

  • Many nodes behind one NAT address pulling at once (new nodes, a scale-out, an upgrade)
  • Images referenced without a registry, so they come from Docker Hub
  • imagePullPolicy: Always on frequently restarted Pods

Confirm with

kubectl describe pod <pod>   # 429 Too Many Requests
kubectl set image deployment/<name> <container>=<mirror>/library/<image>:<tag>
kubectl create secret docker-registry <name> ... and add it to imagePullSecrets

Fix

  1. Pull through a mirror or your own registry: kubectl set image deployment/<name> <container>=<mirror>/library/<image>:<tag>.
  2. Or authenticate the pulls with a docker-registry Secret in imagePullSecrets.
  3. The limit resets over time; deleting Pods to retry only spends more of it.

Prevent it

  • Mirror the public images you use into your own registry, and reference them by that name.
  • Use imagePullPolicy IfNotPresent with immutable tags.

CreateContainerError: apparmor profile not found

Symptom

Pods fail with CreateContainerError on some nodes and run on others.

Error or output

Warning  Failed  kubelet  Error: failed to create containerd container: apparmor profile not found k8s-deny-write

Why it happens

The Pod asks for a Localhost AppArmor profile that is not loaded on its node.

  • The profile was loaded on some nodes only
  • The node rebooted and the profile is not loaded at boot
  • A typo in localhostProfile

Confirm with

kubectl get pods -o wide   # which nodes fail
ssh <node> sudo aa-status
ssh <node> sudo apparmor_parser -q /etc/apparmor.d/<profile>

Fix

  1. Find the nodes without the profile: kubectl get pods -o wide, then sudo aa-status on each.
  2. Load it on every node: sudo apparmor_parser -q /etc/apparmor.d/<profile>.
  3. Correct localhostProfile if the name differs.

Prevent it

  • Install profiles with the node image or a DaemonSet, so every node has them at boot.
  • Label the nodes that have the profile, and select them, if not all do.

Restarting or not Ready

CrashLoopBackOff

Symptom

The Pod is Running for a moment, then shows Error or CrashLoopBackOff, and RESTARTS keeps climbing.

Error or output

orders-6c9b7f5d4-qx8zm   0/1   CrashLoopBackOff   6 (2m ago)   10m
Warning  BackOff  kubelet  Back-off restarting failed container orders in pod orders-6c9b7f5d4-qx8zm_kitchen(<uid>)

Why it happens

The container starts, exits, and is restarted with growing delays.

  • The app errors on start (missing env var, bad config): read the logs
  • Wrong command or args
  • A liveness probe that fails and kills a healthy app
  • OOMKilled (exit code 137)

Confirm with

kubectl logs <pod> --previous
kubectl describe pod <pod>   # Last State, Reason, Exit Code
kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState}'

Fix

  1. Read why the last run ended: kubectl logs <pod> --previous, and Last State in kubectl describe pod <pod>.
  2. Exit code 1 or 2 with an error in the logs: fix the configuration it names, on the Deployment (kubectl set env deployment/<name> KEY=value), so a new rollout replaces the Pods.
  3. Exit code 137 with OOMKilled: raise the memory limit. Killed by a liveness probe: fix the probe, not the app.
  4. Exit code 128 and empty logs: the command itself is wrong (see StartError).

Prevent it

  • Make the app fail fast with a clear message when a required setting is missing.
  • Run the image with production-like configuration in CI, and keep maxUnavailable low so a crashing rollout never takes every replica.

Liveness probe failed, container restarted

Symptom

The app works, yet its container restarts every few minutes; the logs end with a clean shutdown, not a crash.

Error or output

Warning  Unhealthy  kubelet  Liveness probe failed: Get "http://10.244.1.7:8080/healthz": dial tcp 10.244.1.7:8080: connect: connection refused
Normal   Killing    kubelet  Container web failed liveness probe, will be restarted

Why it happens

The kubelet kills containers whose liveness probe fails, even when the app is fine.

  • Probe on the wrong port or path
  • Timeout or failureThreshold too strict for a busy app
  • No startupProbe, so the probe runs before a slow app has started
  • The probe checks a dependency (database, other service) instead of the process itself

Confirm with

kubectl describe pod <pod>   # Unhealthy and Killing events
kubectl logs <pod> --previous   # a clean shutdown means it was killed, not crashed
kubectl get pod <pod> -o yaml | grep -A8 livenessProbe

Fix

  1. Point the probe at the port and path the app really serves: kubectl get pod <pod> -o yaml | grep -A8 livenessProbe.
  2. For slow starters, add a startupProbe so the liveness probe waits until the app is up.
  3. Loosen timeoutSeconds or failureThreshold for an app that is busy but healthy.

Prevent it

  • Let liveness check only the process itself; put dependency checks in readiness.
  • Test probes against the image locally (curl localhost:<port><path>) before shipping them.

OOMKilled

Symptom

The container restarts; Last State says OOMKilled with exit code 137.

Error or output

    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137

Why it happens

The container went over its memory limit and the kernel killed it (exit code 137).

  • The memory limit is lower than the real working set
  • No limit in the manifest, so the namespace's LimitRange default applies
  • A memory leak
  • A runtime heap (JVM, Node.js) set larger than the limit

Confirm with

kubectl describe pod <pod>   # Last State: OOMKilled, and an annotation if LimitRanger set the limit
kubectl describe limitrange
kubectl top pod <pod>
kubectl describe vpa <name>   # if a VPA watches it, read its recommendation

Fix

  1. Raise the memory limit above the real working set: kubectl set resources deployment/<name> --limits=memory=<size> --requests=memory=<size>.
  2. If you set no limit, a LimitRange default did: set one explicitly in the manifest.
  3. Cap runtime heaps below the limit (for example -XX:MaxRAMPercentage=75 for the JVM).

Prevent it

  • Size limits from measured peaks (kubectl top pod, a VPA recommendation) with headroom.
  • Alert on container restarts with reason OOMKilled, and on memory close to its limit.

Running but 0/1 Ready

Symptom

STATUS is Running but READY is 0/1, and the Service sends it no traffic.

Error or output

Warning  Unhealthy  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 404
Warning  Unhealthy  kubelet  Readiness probe failed: Get "http://10.244.2.5:8080/ready": dial tcp 10.244.2.5:8080: connect: connection refused

Why it happens

The readiness probe fails, so the Pod is kept out of its Services.

  • Probe path or port is wrong (404 or connection refused)
  • The app needs longer to start (add a startupProbe)
  • A dependency the readiness check needs is down

Confirm with

kubectl describe pod <pod>   # Readiness probe failed
kubectl get events --field-selector reason=Unhealthy
kubectl logs <pod>   # the probe's requests show up here

Fix

  1. Compare the probe's path and port with what the app serves: kubectl get pod <pod> -o yaml | grep -A8 readinessProbe.
  2. Correct the probe on the Deployment (kubectl edit deployment/<name> or your manifest), so new Pods roll out with it.
  3. If the app needs longer to start, add a startupProbe instead of a long initialDelaySeconds.

Prevent it

  • Give every app a cheap readiness endpoint, and test it in CI.
  • Watch for Pods that stay unready; they shrink capacity without any restart.

Config changed, app still uses the old value

Symptom

You updated a ConfigMap or Secret, but the running app still behaves the old way.

Error or output

MENU_FILE=/etc/menu/summer.json

Why it happens

A ConfigMap or Secret was updated but running Pods did not pick it up.

  • Values in env or envFrom are read once, when the container starts
  • Mounted files update after a delay, but the app only reads them at start
  • A subPath mount never updates

Confirm with

kubectl exec <pod> -- env | grep <KEY>
kubectl rollout restart deployment/<name>
kubectl rollout status deployment/<name>

Fix

  1. Restart the Pods so they read the new value: kubectl rollout restart deployment/<name>.
  2. Check it: kubectl exec <pod> -- env | grep <KEY>.

Prevent it

  • Put a hash of the config in a Pod template annotation (Helm and Kustomize can), so a config change rolls out by itself.
  • Or use immutable, versioned ConfigMaps (menu-config-v2) and change the reference.

Password rejected though the Secret is right

Symptom

The app cannot log in to its database, though the password in the Secret looks right.

Error or output

FATAL:  password authentication failed for user "accounts"

Why it happens

The app gets a different value from the one you meant: usually encoded twice, or with a trailing newline.

  • A base64 value put under stringData:, or passed to --from-literal, so Kubernetes encodes it again
  • echo without -n adds a newline before encoding
  • The Secret was changed but the app read it at start

Confirm with

kubectl get secret <name> -o yaml
echo <value> | base64 -d   # should print the plain value
kubectl create secret generic <name> --from-literal=KEY=<plain value>

Fix

  1. Decode what is stored: kubectl get secret <name> -o jsonpath='{.data.<KEY>}' | base64 -d. If that prints base64 again, it was encoded twice.
  2. Recreate it from the plain value: kubectl create secret generic <name> --from-literal=KEY=<plain value> --dry-run=client -o yaml | kubectl apply -f -.
  3. Restart the Pods so they read it: kubectl rollout restart deployment/<name>.

Prevent it

  • Put plain values under stringData, base64 only under data, and use echo -n when encoding.
  • Create Secrets from files or a secret manager, not by hand.

Now learn it: break and fix it yourself in Secret encoded twice, then take Level 05 · Missing configuration on a real cluster. Open this in the interactive reference.

Read-only file system

Symptom

After hardening, the container exits at start with a read-only file system error.

Error or output

nginx: [emerg] mkdir() "/var/cache/nginx/client_temp" failed (30: Read-only file system)

Why it happens

The container's root filesystem is read-only (securityContext.readOnlyRootFilesystem) and the app writes to it.

  • Hardening turned on for an image that writes caches, pid files or /tmp at start
  • A volume mounted read-only where the app writes

Confirm with

kubectl logs <pod> --previous
kubectl get deploy <name> -o yaml   # securityContext, volumeMounts
Mount an emptyDir at each path the app writes; keep the root read-only

Fix

  1. Keep readOnlyRootFilesystem, and mount an emptyDir at each path the app writes (here /var/cache/nginx, /var/run, /tmp).
  2. Roll out the change on the Deployment and check the logs.

Prevent it

  • Find the paths an image writes before hardening it, by running it with a read-only root locally.
  • Prefer images built to run read-only and as non-root.

Evicted

Symptom

Pods show Evicted (or Error) and are replaced on other nodes; the node has a pressure condition.

Error or output

Status:   Failed
Reason:   Evicted
Message:  The node was low on resource: ephemeral-storage.

Why it happens

The kubelet removed the Pod to protect the node.

  • Node disk pressure, often old images filling /var/lib/containerd
  • Node memory pressure
  • Ephemeral storage use over its limit
  • BestEffort Pods go first, then Burstable over their requests

Confirm with

kubectl describe node <node>   # Conditions and the disk-pressure taint
ssh <node> sudo df -h; ssh <node> sudo crictl rmi --prune
kubectl delete pods -A --field-selector=status.phase=Failed

Fix

  1. Find the pressure: kubectl describe node <node>, Conditions and Taints.
  2. Free the disk: sudo crictl rmi --prune on the node removes unused images; clear large logs.
  3. Clean up the old Pods: kubectl delete pods -A --field-selector=status.phase=Failed.

Prevent it

  • Set requests (and ephemeral-storage limits) so critical Pods are not BestEffort.
  • Alert on node disk use well before the kubelet's eviction threshold.

Now learn it: break and fix it yourself in Node DiskPressure, then take Level 07 · Stuck in Pending on a real cluster. Open this in the interactive reference.

Scheduling and storage

Pending

Symptom

kubectl get pods shows STATUS Pending and NODE <none>, minutes after the Pod was created.

Error or output

Warning  FailedScheduling  default-scheduler  0/3 nodes are available: 3 Insufficient memory. preemption: 0/3 nodes are available: 3 No preemption victims found for incoming pod.
0/3 nodes are available: 1 node(s) had untolerated taint {dedicated: gpu}, 2 node(s) didn't match Pod's node affinity/selector.

Why it happens

The scheduler has not found a node for the Pod.

  • Requests bigger than any node's free capacity (Insufficient cpu/memory)
  • nodeSelector or node affinity matches no node
  • A taint the Pod does not tolerate
  • A PersistentVolumeClaim that is not Bound
  • Too many pods: the node reached its kubelet maxPods

Confirm with

kubectl describe pod <pod>   # FailedScheduling gives one reason per node
kubectl describe nodes | grep -A8 'Allocated resources'
kubectl get nodes --show-labels
kubectl describe node <node> | grep Taints

Fix

  1. Read the FailedScheduling event: it gives one reason per node, and each reason has its own fix.
  2. Insufficient cpu or memory: lower the request to what the app really uses (kubectl set resources deployment/<name> --requests=memory=<size>), or add capacity.

sudo sed -i 's#path: /var/lib/etcd#path: /var/lib/etcd-restore#' /etc/kubernetes/manifests/etcd.yaml
kubectl get pods -A   # refused for a minute while etcd and the API server restart

Fix

  1. Restore into a new, empty directory: etcdutl snapshot restore <file> --data-dir /var/lib/etcd-restore.
  2. Point the etcd static Pod's hostPath volume at it in /etc/kubernetes/manifests/etcd.yaml; the kubelet restarts etcd.
  3. Wait a minute for etcd and the API server, then check with kubectl get pods -A.

Prevent it

  • Practise the restore before you need it, on a test cluster.
  • Keep snapshots off the node, with their date in the file name.

Namespace stuck Terminating

Symptom

The namespace was deleted but stays Terminating, and creating it again is refused.

Error or output

NamespaceFinalizersRemaining   True   SomeFinalizersRemain   Some content in the namespace has finalizers remaining: backup.kitchen.example/protect in 1 resource instances

Why it happens

The namespace was deleted, but something inside it is still waiting for a finalizer to be removed.

  • An operator was uninstalled before its custom resources, so nothing removes their finalizers
  • An APIService (such as metrics) is unavailable, so the namespace cannot list everything to delete
  • A PersistentVolumeClaim or Pod with its own finalizer

Confirm with

kubectl describe ns <ns>   # NamespaceContentRemaining / NamespaceFinalizersRemaining
kubectl api-resources --verbs=list --namespaced -o name | xargs -n 1 kubectl get -n <ns>
kubectl patch <kind> <name> -n <ns> --type=merge -p '{"metadata":{"finalizers":null}}'

Fix

  1. Read what it waits for: kubectl describe ns <ns>.
  2. Delete or fix the remaining objects; bring back their operator if you can.
  3. Only if the operator is gone for good, remove the finalizer from each remaining object: kubectl patch <kind> <name> -n <ns> --type=merge -p '{"metadata":{"finalizers":null}}'.

Prevent it

  • Delete custom resources before uninstalling the operator that owns them.
  • Remove broken APIServices (kubectl get apiservice shows False) so namespaces can be emptied.
